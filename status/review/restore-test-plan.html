Consequence for RPO: with daily backups and no PITR the worst case data loss is up to 24 hours. PITR would bring it to about 2 minutes but costs about USD 100 a month (about GBP 79) for 7 days retention plus a Small compute minimum. That is a recurring liability and is NOT proposed here.

The danger in any copy of production: the cron jobs

A restored copy is a full copy, including cron.job. Eleven jobs call out over HTTP using settings stored in the database, so the copy would call the same production endpoints that production calls: dunning, email-dispatch, onboarding-emails, trial-ending-d1, status-incident-notify, stripe-cleanup-incomplete and others. That could send duplicate customer emails or duplicate billing actions. Supabase's own docs say to disable pg_cron and pg_net work on a cloned project straight after the copy finishes. Every option below handles this explicitly.

Recommendation

Option A, once, before GA. It is the only option that tests the backup we would actually use in a disaster, it costs under GBP 1 one-off and nothing recurring, and it never writes to production. Option B is a useful free supplement later, not a substitute. Option C is rejected.

This spends money, so under RULE 0-G it needs the owner's explicit approval before step 3, with the figure Supabase displays on the confirm screen.

Exact steps for option A

Run as the platform account (platform@velstrian.com) in the Supabase dashboard. Use a stopwatch or write down UTC times at each mark.

  1. Pick a weekday that is not the 1st of the month. Be ready at 12:45 UTC.
  2. Open production velstrian-platform > Database > Backups > Scheduled backups. Write down the timestamp of the newest backup (B). Confirm the PITR tab shows PITR disabled.
  3. At 12:50 UTC: Database > Backups > Restore to a New Project. Pick the newest backup. Read the cost shown, confirm it is under GBP 1 an hour, and confirm. Write down T0 (UTC).
  4. Wait for the dashboard to report the new project as healthy. Write down T1.
  5. Open the new project's SQL editor (never production's, check the project ref in the URL is not gujtuecjzfiqsdnzgyvo).
  6. Immediately run:
    update cron.job set active = false;
select count(*) filter (where active) as still_active from cron.job;
    still_active must be 0. Write down T2. If T2 is after 14:05 UTC, also check production's email log for a duplicate send at 14:10 and report it.
  7. Prove the data, comparing the clone against production (production queries are read only):
    select pg_size_pretty(pg_database_size(current_database()));
select count(*) from auth.users;
select count(*) from information_schema.tables where table_schema = 'public';
select max(created_at) from auth.audit_log_entries;
    Size within a few MB of 419 MB, same user and table counts, and the newest audit row equal to or just before backup time B. Write down T3.
  8. Optional: sign in to the clone's Auth users page and confirm the 4 platform accounts are there. Do not point any app at the clone.
  9. Delete the clone: its Settings > General > Delete project. Write down T4. Billing stops on delete.
  10. Record in the tracker row:
    • RTO = T1 minus T0 (restore), and T3 minus T0 (restore plus verification).
    • RPO = T0 minus B (the age of the newest backup when the restore began, worst case 24 hours).
    • Cost = the hours shown on the org usage page at the next invoice.

What a restore does not bring back

Per Supabase docs: Storage objects (files) are not in the database backup, and Edge Functions, Auth settings, API keys and Realtime settings need setting up again on a new project. For a real disaster where production itself is lost, the runbook must also cover re-pointing the app's environment variables at the new project. That is outside this test and should be its own row if not already covered by the incident runbook.

Exact steps for option B (later, free supplement)

  1. Install PostgreSQL 17 client tools and a local Postgres 17 server.
  2. Off-hours, run pg_dump --format=custom --no-owner against production's session pooler connection string, read from the password manager, never pasted into a file or chat.
  3. pg_restore into a new local database, time it, run the step 7 checks.
  4. Drop the local database and securely delete the dump file the same day.
