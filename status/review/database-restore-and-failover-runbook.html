Database restore and failover runbook

Row: R29-GA-RESTORE-TEST-01. Owner: the founders. Prepared 2026-11-03 by Velstrian Tenderworks.

This page tells you, in plain steps, how to:

  1. Test that our customer database can be brought back from its backup (every quarter, about 30 minutes, a few cents).
  2. Recover for real if the production database is lost or damaged.

You do not need to know databases to follow it. Every click and command is written out.

1. The few facts you need
Production database Supabase project velstrian-platform, ref gujtuecjzfiqsdnzgyvo, region eu-west-1 (Ireland), Micro size
Staging database (test only) ref ipgrnwvfnumgvnxkpxsc
Portal database (internal) ref upxwdxhqzdsjnpsftsfb, separate, not covered here
Backups one full backup every day, kept 7 days. Point in time recovery (PITR) is OFF
Recovery time (RTO), measured 2026-11-03 about 7 minutes for the database to come back in a new project. Allow about 1 hour for a full failover, including pointing the apps at it
Data loss (RPO) up to 24 hours: anything written after the last daily backup (around 04:26 UTC) is lost. PITR would cut this to about 2 minutes but costs about USD 100 a month, not switched on
Cost of a test copy USD 10.18 a month, billed by the hour: about 1.4 cents an hour. A test costs under 5 cents if you delete the copy the same day

Evidence of the first test: docs/release-2.9/ops/restore-tests/2026-11-03.md.

2. What NOT to click

Database > Backups > "Scheduled backups" tab > Restore OVERWRITES production with an old copy. Everything customers did since that backup is gone. Never use it for a test. Only use it in a real disaster, and only after reading section 5.

Never delete, pause or restore a project whose ref is gujtuecjzfiqsdnzgyvo, ipgrnwvfnumgvnxkpxsc or upxwdxhqzdsjnpsftsfb. Check the ref in the browser address bar before every destructive click.

The safe button for a test is the "Restore to a new project" tab. It makes a separate copy and never touches production.

3. The hidden danger: copied timers (cron jobs)

A restored copy is a full copy, including production's 14 timed jobs (pg_cron). They arrive switched on, and 11 of them call the production app, so a copy left running could send customers duplicate emails or repeat billing actions.

On 2026-11-03 all 14 arrived switched on. They were switched off 7 minutes after the copy was created, before any of them fired.

So, for every copy:

  • Start only in a quiet window, when no production job is due for at least 60 minutes.
  • Switch the copy's cron off the moment it answers. The script does this by itself.

4. The quarterly restore test (routine)

When: once a quarter (January, April, July, October), and after any big database change. Who: one founder. Time: about 30 minutes. Cost: under 5 cents.

4.1 One time setup

  1. Sign in to supabase.com as platform@velstrian.com.
  2. Account > Access Tokens > Generate new token. Name it restore-test. Copy it into the password manager. Never paste it into a file, a chat or a ticket.

4.2 Run it

From the velstrian-platform folder, in Git Bash:

# 1. See the plan, the cost and the next safe start time. Calls nothing.
node scripts/ops/restore-test.mjs

# 2. At a safe time, load the token for this terminal only (paste it when asked, it is not shown)
read -s SUPABASE_ACCESS_TOKEN && export SUPABASE_ACCESS_TOKEN

# 3. Run the test
node scripts/ops/restore-test.mjs --execute

What happens:

  1. The script reads production's backup list and counts key tables (read only, it never writes to production).
  2. It checks the quiet window and refuses if a production job is due within 60 minutes.
  3. It asks you for one click, because Supabase does not offer "restore to a new project" through its API:
    • open the link it prints (production > Database > Backups > Restore to a new project tab),
    • pick the newest backup,
    • name the project velstrian-platform-restoretest-<yyyymmdd> (the name must start with velstrian-platform-restoretest),
    • read the cost, click Continue, then press Enter in the terminal.
  4. It finds the new project, waits until it answers (that time is the RTO), switches off all its cron jobs, clears its outgoing web request queue, and proves 0 jobs are active.
  5. It compares row counts with production and writes the evidence to docs/release-2.9/ops/restore-tests/<date>.md and .json.
  6. It deletes the copy, but only after checking the ref is not production, staging or portal and the name starts with velstrian-platform-restoretest.

If you want to look around the copy first, add --keep, and delete it later with:

node scripts/ops/restore-test.mjs --teardown <copy ref>

Or by hand: open the copy (check the ref in the address bar is NOT one of the three protected refs)

Project Settings > General > Delete project.

If the script stops with an error after the copy exists, switch the copy's cron off by hand straight away: open the copy's SQL editor (check the ref again) and run

select cron.alter_job(jobid, active := false) from cron.job;
select count(*) from cron.job where active;   -- must be 0

then delete the copy.

4.3 After the test

  • Commit the evidence file and note RTO, RPO and cost in the tracker row.
  • Confirm on the org billing page next month that the copy appears only for those hours.

5. Real failover: production is lost or damaged

5.1 Decide what happened (5 minutes)

Is production up at all? (dashboard shows the project, the app loads)
|
+-- YES, but data is wrong (bad import, deleted rows, a bad migration)
|     |
|     +-- Only a few rows or one table?  -> Do NOT restore. Make a test copy (section 4,
|     |                                     --keep), copy the missing rows back by hand.
|     |                                     No customer data written today is lost.
|     |
|     +-- Widespread damage?             -> 5.2 option A (new project), or B if A is impossible.
|
+-- NO, the project is gone, broken or unreachable for more than 30 minutes
      (check status.supabase.com first: if Supabase itself is down in eu-west-1, wait,
       a restore would land in the same region)
      -> 5.2 option A.

Point in time or daily backup? PITR is OFF, so the only choice is a daily backup. Pick the newest backup taken before the damage started. Anything after that backup is lost (up to 24 hours).

5.2 Restore

Option A (preferred): restore into a NEW project. Production stays untouched, so you can still pull data from it later and you can roll back.

  1. Production > Database > Backups > Restore to a new project tab > pick the backup > name it velstrian-platform-recovered-<yyyymmdd> > Continue. Note the time.
  2. About 7 minutes later, open the new project's SQL editor. Keep the cron jobs ON this time only if production is truly dead (they are the real jobs now). If old production is still running its own jobs, switch the new project's cron off until the switchover in step 5.3 is done, then switch it back on with select cron.alter_job(jobid, active := true) from cron.job;.
  3. Set again on the new project, because a restore does not copy them:
    • Authentication settings: site URL, redirect URLs, email (Brevo SMTP), MFA and passkey settings, providers.
    • Storage buckets and files. Files are not in the database backup. If old production is still reachable, copy the buckets across. If it is gone, uploaded files are lost.
    • Edge Functions and their secrets, if any.
    • Network restrictions and SSL enforcement (normally copied, check them).

Option B (last resort): restore over production ("Scheduled backups" tab > Restore). Use only if a new project cannot be created. Production is offline while it runs, and everything after the backup is lost permanently. No app repointing is needed afterwards.

5.3 Point the apps at the new project (Option A only)

Get the new project's URL and keys from its Project Settings > API (and Database for the connection string).

Where What to change
Railway, API service, production environment SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, SUPABASE_JWT_SECRET, SUPABASE_PROJECT_REF_PRODUCTION, and any database connection string
Vercel, project crowagent-platform-web, Production NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY
Vercel, project crowagent-portal only if one of its variables names gujtuecjzfiqsdnzgyvo (the portal normally uses its own database)

Vercel only picks up new values on a new deploy. Redeploy through the normal path only: pnpm staging:promote, then pnpm prod:promote with the owner's approval text carrying the sha (RULE 0-P). On Railway, changing a variable redeploys the service by itself.

Not affected, no change needed:

  • Stripe webhooks and Brevo webhooks point at our app URLs, not at Supabase.
  • DNS: nothing changes. The app domains stay the same.

What customers notice: everyone is signed out once (the new project has new signing keys) and signs in again. Data written after the backup is missing.

5.4 Check it worked (15 minutes)

  1. Sign in to the app with a platform account.
  2. Open a bid, upload a small document, check the dashboard loads.
  3. In the new project's SQL editor: select count(*) from cron.job where active; should be 14 (the real jobs are now running here) and select max(created_at) from public.audit_logs; should move as you use the app.
  4. Check Sentry for new errors.

5.5 Rollback

If the new project misbehaves and old production is still alive: put the old values back in Railway and Vercel (keep a copy of the old values before step 5.3), redeploy, and switch the new project's cron off. Do not delete either project until the incident is closed.

5.6 Who does what

Step Who About how long
Decide (5.1) and declare the incident founder on call 5 minutes
Restore click (5.2) founder with Supabase access 2 minutes, then about 7 minutes waiting
Auth, storage, functions (5.2 step 3) same founder 15 minutes
Railway and Vercel variables, redeploy (5.3) founder with Railway and Vercel access 15 to 20 minutes
Checks (5.4) the other founder 15 minutes
Tell customers (status page and email if data was lost) founder on call 15 minutes

Total: about 1 hour from decision to working app, of which the database itself is about 7 minutes.

5.7 Evidence to keep

  • Times: damage noticed, decision, restore clicked, copy answered, apps switched, checks passed.
  • Which backup was used and its timestamp (that is the data lost).
  • The old and new project refs.
  • Screenshots of the backup chosen and of the checks.
  • File it under docs/release-2.9/ops/restore-tests/ as <date>-incident.md and link it from the incident row. If personal data was lost, the 72 hour breach notice process applies.
