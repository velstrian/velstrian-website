Corrections 2026-10-17What changed and why

Corrections 2026-10-17. The first version of this plan treated the company as if it had customers, live subscriptions and user sessions to protect. The owner rejected that. It is wrong, and this revision removes everything that rested on it.

Facts the corrections rest on

  • Production carries the four platform accounts and paying customers only, and there are no paying customers (workspace CLAUDE.md, RULE 0-P).
  • The Stripe LIVE account has exactly 1 subscription ever (sub_1TI9Rk..., canceled 2026-05-01, reason payment_failed) and ZERO active. This was measured by the coordinator on 17 October 2026 and replaces the older 2026-08-22 note, which gave a different cancel date (owner memory note project_stripe_live_account_has_zero_subscriptions).
  • The next release is the first real customer onboarding. Signup is invitation only and production held one organisation (owner memory note project_next_release_real_customer_onboarding, 2026-09-29).
  • One measured nuance: invited beta testers reach STAGING through invite links to staging-app.crowagent.ai (owner memory note project_beta_onboarding_two_gates_and_an_expired_token, 2026-09-22). They are the only people a URL change can touch, so the plan keeps one courtesy message to them.

What changed

  • Trade mark: the core path and core cost are UK only. The EU filing is optional and deferred, with the 6 month Paris priority window explained (section 8).
  • Code effort is now estimated from a MEASURED read-only dry run, not a feel. The dry run applied the replacement map in memory to every candidate file in the three repos: 3,585 files and 19,731 replacements, of which 1,239 test files (7,410 replacements) and 2,346 non test files (12,321 replacements). It ran end to end in 65 seconds. Edit time and machine time are shown separately. Effort fell from 17 sessions and 18.4M tokens (first version) to 5 sessions, about 16 edit hours, about 7 machine hours and about 7.1M tokens.
  • The dry run also found what a blind replace would break, so the codemod needs a reviewed exclusion list: 215 uses of the crowagent.platform@gmail.com identity in 156 files (a velstran.platform mailbox does not exist), 152 generated vercel.app URLs, 1,751 sibling folder tokens such as crowagent-website in 481 files, and 43 file names that contain the old name, of which at least 17 are logo images only the owner can replace.
  • Territory: a UK registration protects the UK and the Isle of Man only, per gov.uk (S26). That line is no longer marked unverified.
  • Internal names now change too: the @crowagent scope, CROWAGENT_ env var names, Stripe lookup keys and product names, vendor project names and repository names. The keep list shrank to the few names a measured technical constraint forces, each named precisely in section 5.
  • Removed: the 30 to 90 day run of both domains, the passkey lockout worry, the additive only vendor sequencing, sender warm up and dual sending, the customer notice, the 12 month decommission phase. The old domain stays only as a 301 source for SEO and inbound links.

Section 2Decisions the owner must make

Each decision is a question with options and one recommended answer. None is settled by this page.

D1. Is Velstran the final name, subject to clearance?

  1. Go only if the register clearance and an attorney review are clean (Gate 0)
  2. Go now and accept the risk
  3. Pick another name

Recommended: Option 1. A second opposed application would cost another cycle, and clearance costs far less than that.

D2. CrowMark and CrowMark Buyer both contain the stem Crow. Rename them too?

  1. Keep both names for now
  2. Rename both in this same programme (needs two new names cleared)
  3. Keep for now and decide after the CrowAgent opposition grounds are read

Recommended: Option 3. Read who opposed and on which element first. If the grounds cite the Crow stem, take option 2 inside this programme. The dry run measured that it is NOT a cheap extra: CrowMark, crowmark and CROWMARK appear in 5,239 files with 69,881 replacements (2,439 of them test files), and 90 distinct crowmark_ tables exist in the migrations, plus routes. It needs a forward migration and route redirects, about 2 extra sessions, 8 edit hours, 3 machine hours and 4M tokens. A second rebrand later would still repeat the whole verification chain. The owner decides.

D3. Which domains to buy and where?

  1. velstran.com, velstran.co.uk, velstran.uk at Porkbun (USD 22.40 year one)
  2. Add velstran.ai (USD 82.70 a year) and velstran.app
  3. Different registrar

Recommended: Option 1. Porkbun is the only registrar whose first year and renewal prices were verified here. DNS stays on the free Cloudflare plan, never Cloudflare Registrar.

D4. Primary public domain

  1. velstran.com with app.velstran.com and portal.velstran.com
  2. velstran.co.uk
  3. velstran.ai

Recommended: Option 1. The two UK domains redirect to it.

D5. Trade mark territory and route

  1. UK only now, with an EU decision deadline of 6 months after the UK filing date
  2. UK now plus an EU filing now
  3. UK plus EU and WIPO later through Madrid

Recommended: Option 1. A UK registration protects the UK and the Isle of Man only (S26). Trading in the EU does not by itself require an EU mark, an EU mark adds enforcement rights there (owner statement). The Paris Convention gives 6 months from the first filing to file abroad with the same priority date (S24). Diarise that date and file in the EU when the EU becomes a real market. Classes 9, 35 and 42 are an assumption to confirm with the attorney.

D6. Order of company name change versus trade mark filing

  1. File the trade mark first, then change the company name
  2. Change the company name first
  3. Same week

Recommended: Option 1. Filing fixes the date. The name change is a same day online filing.

D7. What happens to the opposed CrowAgent application?

  1. Let counsel advise on withdrawing, defending or letting it lapse
  2. Withdraw now
  3. Defend

Recommended: Option 1. This is procedure and money that only the owner and a trade mark attorney can decide.

D8. Dated historical records (RELEASE trackers, RESUME-STATE files, forensic audits) and the local folder name

  1. Replace the name in live code and live docs, leave dated records untouched with one note at the top of the live guide, and rename the local folder last outside agent sessions
  2. Rewrite everything including dated records
  3. Keep the local folder name for good

Recommended: Option 1. Dated records quote old URLs as evidence. The folder constraint is measured: 1,751 sibling folder tokens (crowagent-platform, crowagent-website, crowagent-data, crowagent-branding) in 481 files, plus 14 tooling files that hold the absolute path (scripts/r284-*.cmd, .claude/agents/*.md, both settings.local.json, status/start-tracker.cmd, status/issues.json). Either rename the folders in the same step as the replace or exclude those tokens.

D9. Cutover shape

  1. One cutover at the single production deploy, with crowagent.ai kept only as a 301 source
  2. Run both domains side by side for a window

Recommended: Option 1. There are no users to lock out. The four platform accounts re-login and re-enrol passkeys once.

D10. The platform mailbox crowagent.platform@gmail.com and the identity rule in CLAUDE.md

  1. Create a new platform identity and restate the rule
  2. Keep the mailbox as an internal identity

Recommended: Option 2 for now. The rule names this identity and only the owner can change it. Whether a Gmail address can be renamed is UNVERIFIED, so a new mailbox plus forwarding is the route if wanted.

D11. Owner supplied artwork

  1. Owner provides the Velstran mark, wordmark and favicon
  2. Claude proposes concepts

Recommended: Option 1. RULE 0-C forbids inventing a brand value. Colours stay frozen per the owner decision of 2026-08-11.

D12. Push and deploy budget for this programme (RULE 0-G, RULE 0-P)

  1. 2 pushes (platform, website), 1 staging promote and 1 production promote, each with its own approval
  2. More

Recommended: Option 1. The staging promote needs no push. Costs are stated again before each ask. The production promote covers two Vercel projects, so confirm the R2.8.5 deploy count before asking.

Product names: CrowMark and CrowMark Buyer

CrowMark and CrowMark Buyer both contain Crow. The CrowAgent application was opposed, but the grounds are not known to this research. If the opposer relied on the Crow element, the CrowMark names carry the same exposure and renaming only the company would move the problem instead of removing it. If the opposer relied on Agent or on a descriptive overlap, CrowMark may be unaffected.

  • A. Keep both names (cheapest, exposure unknown)
  • B. Rename both inside this programme (two cleared names needed, about 2 extra sessions, 8 edit hours, 3 machine hours, 4M tokens, a forward migration for 90 crowmark_ tables, route redirects and a second clearance)
  • C. Keep for now, decide at Gate 0 after the grounds are read

Recommendation as a question: choose C, then B if the grounds cite the Crow element. The dry run shows it is far larger than the company rename (5,239 files, 69,881 replacements, 90 tables), so it is a real work package, but doing it later would repeat the build, the targeted pass, the certification and both deploys. The owner decides.

How central the name really is (RULE 0-C)

  • Colour: central. packages/tokens/brand/brand.source.json is the one source, gen-brand.mjs writes tokens.css, constants.ts and the copy in crowagent-website/astro/src/styles (packages/tokens/package.json brand comment).
  • Contact identity: central. packages/tokens/src/contact.ts holds SUPPORT_EMAIL, SALES_EMAIL, SECURITY_EMAIL and the From name. attribution.ts holds the document footer. Both are imported through @crowagent/tokens, which has 44 import lines across web and apps.
  • Wordmark and legal line: not central. email-shell.ts lines 124 to 140 hard code the text CrowAgent and the company line. No BRAND_NAME or COMPANY_NAME constant exists in web/src.
  • Logo: duplicated. CrowAgentLogo.tsx exists in web/src/shared/ui and apps/portal/src/components.
  • Python side: partly generated. api/app/services/_email_shell_generated.py and regulated_constants_generated.py show a generator pattern, but api/app/config.py hard codes the addresses and the default sender display name.
  • Website: astro/src/data/site.ts holds 15 hits and pages repeat the name. The website keeps its own copy of brand.source.json.
  • Consequence now: a script reaches all of it in one pass, so centralising is not on the critical path. WP4 adds the identity constants block so that a future change is one edit.

Guard test design

  • Add an identity block to brand.source.json (name, legalName, formerName, primary domain, mailbox addresses) and let gen-brand.mjs emit it for TypeScript, Python and astro. brand:check already fails on drift.
  • Guard test: scan the code roots (web/src, apps/portal/src, api/app, packages, astro/src) with comments stripped for crowagent, Crow Agent and CrowAgent, case insensitive. Fail on any hit outside a short allowlist of patterns, not a count.
  • Allowlist patterns: the supabase/migrations tree, the redirect map file, the formerly known as legal line, and fixtures that assert the absence of the old name.
  • Red prove it: add a raw old name to a component, show the test fail, remove it. Run it locally through pnpm. Per RULE 0-G it ships in the same commit as the product change, it is a pattern allowlist and not a numeric baseline, and wiring it into CI needs separate owner approval.
